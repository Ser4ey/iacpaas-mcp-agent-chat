# Запись в IACPaaS: защита базовых ресурсов и подтверждение пользователя

Описание для реализации. Утверждено автором проекта в чате 28.10.2026. Пометка «(решение исполнителя-проектировщика)» означает выбор, сделанный при проектировании без отдельного обсуждения: его можно пересмотреть.

## Зачем

Задание требует от MCP-сервера разделить читающие и изменяющие инструменты и для изменяющих операций предусмотреть подтверждение пользователя или явный барьер политики. Среди тестовых сценариев задания — «Изменяющая операция с обязательным подтверждением». Сейчас проект только читает. HTTP API платформы запись поддерживает, поэтому её нужно реализовать.

Ожидаемая проверка преподавателя: «Модель может создать ресурс? А прочитать? Создай что-нибудь. Теперь прочитай». Реализация — минимальная, но законченная под этот сценарий.

Главный принцип: **MCP-сервер скрывает от модели сложность API платформы.** Модель работает в терминах предметной области (папка, ресурс по онтологии, понятие онтологии, имя, значение, путь вершины) и никогда не пишет JSON платформы. Пользователь тоже.

## Сценарий демонстрации (критерий готовности)

1. «Создай в моём фонде папку „Демо агента“ и в ней ресурс „Мои свойства“ по онтологии базы свойств: класс „Тепловые свойства“, свойство „Теплопроводность“, единица измерения „Вт/(м·К)“». Агент читает структуру онтологии (`get_inforesource`), создаёт папку (карточка «Подтвердить / Отменить» → «Подтвердить»), создаёт ресурс с содержимым (карточка → «Подтвердить»).
2. «Прочитай его» — агент читает ресурс по пути живым чтением и показывает дерево.
3. «Переименуй свойство в „Теплопроводность λ“» — карточка → «Подтвердить», агент перечитывает и показывает результат.
4. «Удали Справочник по материалам» — сразу отказ `PROTECTED_RESOURCE`, карточки нет, к платформе нет ни одного запроса на запись.
5. «Удали „Мои свойства“» — карточка → «Отменить», ничего не изменилось; повтор → «Подтвердить» → ресурс в корзине.

## Что решил автор

- **Два записывающих инструмента:** `write_inforesource` — создание и изменение, `delete_inforesource` — удаление.
- **Модель и пользователь не пишут JSON:** его собирает сервер.
- **Где можно писать — весь «Мой фонд», кроме защищённых ресурсов** (не папка-песочница).
- **Базовые ресурсы защищены от удаления и изменения**, даже если права платформы это позволяют.
- **Ручное подтверждение в интерфейсе на уровне реализации MCP.**
- **Чтение любого ресурса фонда по пути**, без подтверждения чтения (листинга папок в API нет, путь агент узнаёт от пользователя или из своей записи — это обоснование, а не правило в коде).
- **Утверждён этот минимальный вариант** целиком, включая решения ниже.
- **Разрешена живая проверка на платформе** в папке «Демо агента» в корне «Моего фонда»; удалять только созданное в ходе проверки.

## Решения исполнителя-проектировщика (утверждены вместе с вариантом)

- Подтверждение — MCP elicitation (`ctx.elicit`). Если в режиме `stateless_http=True, json_response=True` сервер не может запросить подтверждение посреди вызова, перевести HTTP-транспорт в режим с сессией (`stateless_http=False`, `json_response=False`).
- Запись и чтение по пути включаются флагом `WRITE_ENABLED`, **по умолчанию `true`** (на защите ничего не настраивать). `WRITE_ENABLED=false` — режим только чтения ровно как сейчас: записывающих инструментов и параметра `path` у чтения нет.
- Защищённые пути: пути ресурсов из `config/resources.json`, папка «Загрузки» целиком, пути из `PROTECTED_PATHS` (через `;`).
- Время на подтверждение — 120 секунд (`WRITE_CONFIRM_TIMEOUT_SECONDS`).
- Аннотации MCP: у читающих инструментов `readOnlyHint: true`; у обоих записывающих `readOnlyHint: false`, `destructiveHint: true` (по определению MCP `false` значит «только добавляет», а изменение вершины меняет существующее).
- Структура онтологии для модели — в результате `get_inforesource` для онтологии (без нового инструмента). Всего инструментов 9: 7 читающих и 2 записывающих.

## Не делаем (явно)

- Добавление вершин в уже существующий ресурс (создание сразу с содержимым покрывает сценарий).
- Копирование фрагментов, импорт произвольного JSON.
- Удаление и очистку подграфов, очистку ресурса.
- Ссылки на вершины других ресурсов при создании (например, «Химический элемент» в составе марки) — понятный отказ `UNSUPPORTED_ONTOLOGY_FEATURE`.
- Проверку множественности (`specifier`) по онтологии.
- Онтологии вне трёх онтологий проекта для `create_resource`.
- Запуск сервисов платформы, листинг фонда, поиск и подсчёт по небазовым ресурсам, удаление и переименование папок, пакетные операции, подтверждение чтения, VS Code.

## Анти-цели

- Запись в защищённый путь выполнена — при любом написании пути.
- Запись выполнена без явного «Подтвердить»: модель подтвердила сама, истекло время, клиент не умеет подтверждение, нажат «Стоп» или закрыта страница.
- Карточка описывает не ту операцию, которая выполняется.
- Сервер создаёт ресурс, не соответствующий онтологии, вместо понятного отказа.
- Ломаются существующие инструменты чтения, сохранённые диалоги или текущие тесты (142).

## Платформа

Проверено 28.10.2026 по [RemoteCalls.html](https://iacpaas.dvo.ru/docs/RemoteCalls/RemoteCalls.html) и OpenAPI (`https://iacpaas.dvo.ru/v3/api-docs`). Авторизация как у экспорта (`Authorization: Bearer …` или `X-API-KEY`). Работа только с ресурсами этого пользователя; обработка запроса — до 30 секунд, таймаут соединения не меньше.

| Операция | Запрос | Тело (JSON) |
|---|---|---|
| Создание папки | `POST /api/storage-unit/folder/create` | `path`, `name`, `description`, `metainfo` (только в OpenAPI: «создает новую папку в МФ пользователя») |
| Импорт ресурса | `POST /api/data/import` | `path` — папка-контейнер в «Моём фонде» (без `<e-mail>/Мой Фонд/` и без имени ресурса), `json` — ресурс в universal JSON строкой, `clearIfExists` |
| Изменение вершины | `PUT /api/data/update` | `path` — ресурс, `concept_path` — путь до вершины, `metaconcept_path` — путь из меток мета-вершин для вершин `concept_path`, `mark` (новая метка), `comment` (новый комментарий) — оба необязательные |
| Удаление | `DELETE /api/data/delete` | `path` — ресурс, `mode`: `trashIR` (в корзину), `deleteIR` (совсем) |

Ответ импорта, изменения и удаления — `CodeResult {success, code, error, explanation, explanationSafe, platformUnavailable}`, создания папки — `Result` (без `code`). Пример universal JSON — выгрузка корня «Базы свойств материалов» в `.research/export_probe_4640160026398263790.json`: `title`, `json_type: "universal"`, `ontology: "<account> / Мой Фонд / Загрузки / Онтология …$;"`, `type: "КОРЕНЬ"`, `name`, `meta`, `successors` (у вершин `type`, `name`, `meta`, `comment`, у значений — значение). Формат — [Json.html](https://iacpaas.dvo.ru/docs/Json/Json.html).

**Проверить первым делом на платформе** (в папке «Демо агента»):
- что означает `path` у создания папки (родитель?) и как задаётся имя импортируемого ресурса (`title` корня?);
- какой минимальный universal JSON принимает импорт для нового ресурса: нужны ли `id`, как указывается онтология, как записываются значения `ТЕРМИНАЛ-СОРТ` (`REAL`, `STRING`);
- формат `concept_path` и `metaconcept_path` у `update` (начинается ли с `/`, экранирование имён с `/` — у экспорта тройные кавычки ‴…‴, `docs/api-mapping.md`);
- какие поля `CodeResult` заполнены при отказе.

## Часть 1. Политика записи

На сервере, в общей для stdio и HTTP доменной логике, до подтверждения и до обращения к платформе.

- **Нормализация пути:** сегменты по `/`, обрезка пробелов, без пустых сегментов, сравнение без учёта регистра; префикс «Мой Фонд» (и `<e-mail>/Мой Фонд`) снимается или запрос отклоняется. Имена с `/` в тройных кавычках — один сегмент.
- **Защищён** путь, совпадающий с защищённым или лежащий внутри защищённой папки (по сегментам). Проверяются: у создания папки и ресурса — родитель и итоговый путь; у изменения и удаления — путь ресурса. Отказ — `PROTECTED_RESOURCE` с названием правила.
- **Чужие вершины:** `update_concept` меняет только вершину, принадлежащую самому ресурсу; ссылка на вершину другого ресурса (поле `original`) — отказ `FOREIGN_CONCEPT`. Неоднозначный путь (одноимённые соседи) — `AMBIGUOUS_PATH`.
- Каждая попытка записи пишется в журнал сервера одной строкой без секретов.

## Часть 2. Инструменты

**`write_inforesource`**, аргумент `operation` (у каждого варианта свои обязательные поля в JSON Schema):

| `operation` | Поля | Что делает сервер |
|---|---|---|
| `create_folder` | `parent_path` (пусто — корень фонда), `name`, `description` (необязательно) | Создаёт папку |
| `create_resource` | `folder_path`, `name`, `ontology` (`materials_ontology`, `properties_ontology` или `characteristics_ontology`), `comment` (необязательно), `items` (необязательно) — дерево: `concept` (имя понятия онтологии), `name` (для вершин) или `value` (для значений), `comment`, `children` | Проверяет дерево по онтологии: понятие допустимо под родителем (включая варианты альтернативы и понятия по `link` внутри трёх онтологий проекта), у вершины есть имя, тип значения подходит (`REAL` — число, `STRING` — строка). Собирает universal JSON и импортирует |
| `update_concept` | `path` (ресурс), `concept_path`, `name` и/или `value`, `comment` | Читает вершину, проверяет принадлежность ресурсу и тип значения, вычисляет `metaconcept_path`, вызывает `update` |

**`delete_inforesource`**: `path`, `mode` — `trash` (по умолчанию) или `delete`.

**Ошибки — с подсказкой:** отказ по онтологии называет, что допустимо в этом месте («в „Свойство“ нельзя добавить „Плотность“; допустимы: …»). Коды: `PROTECTED_RESOURCE`, `FOREIGN_CONCEPT`, `AMBIGUOUS_PATH`, `CONCEPT_NOT_ALLOWED`, `INVALID_VALUE`, `UNSUPPORTED_ONTOLOGY_FEATURE`, `NODE_NOT_FOUND`, `INVALID_ARGUMENTS`, `CONFIRMATION_DECLINED`, `CONFIRMATION_TIMEOUT`, `CONFIRMATION_UNAVAILABLE`, `PLATFORM_REJECTED`, `PLATFORM_UNAVAILABLE`, `PLATFORM_TIMEOUT`, `ACCESS_DENIED`.

**Результат** — `ToolResult`: при успехе `data` с операцией, путём и ответом платформы, `meta.served_from: iacpaas_live`; после записи кэш живого чтения по ресурсу сбрасывается.

**Чтение.** `get_inforesource` и `get_subgraph` принимают либо `resource_id` (как сейчас), либо `path` в «Моём фонде». Чтение по пути — только живое, без индекса и без запасного снимка; корень подграфа — путь вершины (`start-target-concept-path`); у вершин в результате — `concept_path`. Пределы глубины и числа вершин — как сейчас. `get_inforesource` для онтологии (трёх онтологий проекта) дополнительно отдаёт компактную структуру: дерево понятий с видом (вершина с именем, значение и его тип, вариант альтернативы).

**Описания для модели:** писать можно в любом месте «Моего фонда», кроме защищённых ресурсов; каждая запись требует подтверждения пользователя; перед созданием прочитать структуру онтологии через `get_inforesource`; вершины брать из результатов чтения, не угадывать.

## Часть 3. Подтверждение (MCP elicitation)

- **Сервер:** после проверок вызывает `ctx.elicit(...)`. Сообщение строит сервер из фактических аргументов, человеческим языком: «Создать папку „Демо агента“ в корне фонда», «Создать ресурс „Мои свойства“ в „Демо агента“ по онтологии „Онтология базы свойств материалов“: Класс свойств „Тепловые свойства“ → Свойство „Теплопроводность“ → единица измерения „Вт/(м·К)“», «Переименовать …», «Удалить в корзину ресурс …». Запись только при `accept` с подтверждением. `decline`/`cancel` → `CONFIRMATION_DECLINED`; клиент без elicitation или сбой → `CONFIRMATION_UNAVAILABLE`; 120 с без ответа → `CONFIRMATION_TIMEOUT`.
- **Первый шаг реализации — проба транспорта:** клиент MCP SDK по HTTP и stdio, инструмент с `ctx.elicit`, ответы «принять» и «отклонить»; при необходимости — режим с сессией.
- **Агент и веб:** `mcp_tools` передаёт `elicitation_callback`, привязанный к ходу; обработчик шлёт в поток хода событие `confirm_request` (`id`, текст, инструмент, время до отмены) и ждёт решения. Решение — `POST /api/sessions/{id}/confirmations/{confirmation_id}` с `{"accept": true|false}`, работает при занятой блокировке диалога. «Стоп» или закрытая страница — отказ. Неизвестный или решённый `confirmation_id` — `404`. У модели нет пути подтвердить самой.
- **Интерфейс:** карточка в журнале хода у вызова: описание, «Подтвердить» и «Отменить» (у удаления — цвет опасности), обратный отсчёт; после решения — итог, он сохраняется в журнале хода. Несколько записей сразу — у каждой своя карточка.
- **Другие MCP-клиенты:** с поддержкой elicitation показывают свой запрос; без неё запись невозможна (`CONFIRMATION_UNAVAILABLE`).

## Часть 4. Промпт и настройки

- **Промпт:** запись только по явной просьбе пользователя; перед созданием прочитать структуру онтологии, перед изменением — вершину; предупредить о подтверждении; после записи перечитать и показать; отклонённое не повторять без новой просьбы; на `PROTECTED_RESOURCE` объяснить защиту базовых ресурсов.
- **Настройки** (`config.py`, `.env.example`, таблица настроек в `docs/guide.html`): `WRITE_ENABLED` (`true`), `PROTECTED_PATHS` (пусто), `WRITE_CONFIRM_TIMEOUT_SECONDS` (120).

## Проверка готовности

**Автоматические тесты** (без сети и платных запросов):
- матрица защиты: каждая операция × защищённый ресурс, «Загрузки», вложенный путь, `PROTECTED_PATHS`, обходные написания (без пробелов вокруг `/`, регистр, лишние `/`, префикс «Мой Фонд») — отказ, подменённая платформа не получила запроса на запись;
- онтология на настоящих онтологиях проекта из индекса: структура в `get_inforesource`; допустимое дерево собирается в верный JSON; недопустимое понятие и неверный тип значения — отказ с подсказкой; неподдерживаемое — `UNSUPPORTED_ONTOLOGY_FEATURE`;
- каждая операция строит верный запрос к платформе (метод, адрес, тело), ответы и ошибки платформы переводятся в коды; `update_concept` вычисляет `metaconcept_path`, отказывает на чужой вершине;
- подтверждение: принято → запрос ушёл; отклонено, истекло время, клиент без elicitation → запроса нет, верный код;
- `WRITE_ENABLED=false` → записывающих инструментов и параметра `path` нет в `list_tools`;
- чтение по пути: живое чтение, `concept_path` у вершин, ошибка при недоступной платформе;
- сквозной тест «HTTP → агент → настоящий MCP-сервер» с записью: `confirm_request` в потоке, решение через эндпоинт, итог в журнале;
- все прежние тесты зелёные.

**Живая проверка** — в папке «Демо агента» (разрешено автором): сначала пункты «Проверить первым делом», затем сценарий демонстрации через чат в браузере. Удалять только созданное. Результат — новый датированный раздел в `docs/verification.md`.

В его план добавляются исключения: записывающие вызовы никогда не считаются повтором, чтение после успешной записи выполняется заново. Пункт README «План доработок» дополняется ими.

## Документация

Только текущее поведение, без «раньше было так» (датированные разделы `docs/verification.md` не переписываются): `README.md` (запись, защита, подтверждение, чтение по пути, настройки, раздел о подключении MCP к другим агентам, «План доработок»), `docs/api-mapping.md` (строки сопоставления, «Что намеренно отсутствует», `write_inforesource` из задания), `docs/architecture.md` («Политика доступа», «Соответствие заданию»), `docs/http-api.md` (`confirm_request`, эндпоинт решения, коды), `docs/scenarios.md` (сценарий демонстрации), `docs/guide.html` (число инструментов — сейчас «7» и «семь» в нескольких местах, таблица инструментов, настройки, вопросы к защите, число тестов), `.env.example`.

## Ограничения

- Python 3.12, зависимости из `requirements-lock.txt`; новые пакеты — только при необходимости.
- Секреты не попадают в результаты инструментов, журнал и сообщения подтверждения.
- Сохранённые диалоги продолжают открываться.
- На настоящей платформе создавать, изменять и удалять — только в папке «Демо агента» и только созданное в проверке.

## Оставлено исполнителю

Имена внутренних классов и модулей; точная форма JSON Schema (при явных обязательных полях у вариантов); формат структуры онтологии в `get_inforesource`; как событие подтверждения доходит из обработчика elicitation до потока SSE; тексты карточки и стили; формулировки описаний и промпта; порядок реализации — но проба транспорта и пункты «Проверить первым делом» первыми.
