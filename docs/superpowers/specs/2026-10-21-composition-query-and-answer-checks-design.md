# Поиск марок по составу и проверка ответов

Описание для реализации. Согласовано с автором проекта в чате 21.10.2026. Пометка «(решение исполнителя-проектировщика)» означает выбор, сделанный при проектировании без отдельного обсуждения: его можно пересмотреть.

## Зачем

1. **Вопросы по параметрам состава.** Пользователь спрашивает: «выведи материалы, где хрома больше 20 %», «топ-3 по хрому», «материалы, где есть хром, но нет никеля», «найди материалы с интересными названиями, где железа больше 25 %». Сейчас у модели нет инструмента, который подбирает марки по условиям на состав. `search_graph` ищет только по словам, отдаёт до 20 вершин за раз и сортирует по релевантности, а не по значению. Модель собирает ответ из страниц поиска, и на больших выборках это ненадёжно. Реальный пример: вопрос «3 материала с самой высокой плотностью» занял 17 вызовов с ошибкой `limit`, повторами одинаковых поисков и чтением за пределами результатов.
2. **Проверка ответов на галлюцинации в runtime.** Сейчас есть только признак `grounded`: был ли хоть один успешный вызов инструмента. Соответствует ли текст ответа данным, никто не проверяет.

## Цели

1. MCP-инструмент, которому модель передаёт структуру условий на состав и получает список подходящих марок (первую страницу, если их много). Это один из шагов модели: дальше она сама выбирает, сравнивает, читает записи.
2. Автоматическая сверка чисел в каждом ответе с данными, полученными из базы. Результат виден под ответом.
3. Кнопка «Проверить» у конкретного ответа: отдельный агент-проверяющий сравнивает ответ с тем, что реально пришло из базы, и выдаёт вердикт с долей подтверждённых утверждений.
4. Исправить ложный признак `fields_truncated` у вершин со ссылками (см. часть 4).
5. Мелкие правки описаний, промпта и журнала, а во втором заходе — защита от повторных вызовов и проверка устаревания индекса (см. «Объём по заходам»).

## Не цели

- Произвольный язык запросов (модель не пишет SQL или Cypher).
- Условия по свойствам материалов (плотность, температуры и т. п.). Свойства заполнены только у 7 марок из 1 334, и для них нужен пересчёт единиц. (Решение исполнителя-проектировщика.)
- «ИЛИ» между условиями: все условия соединяются через «И», для «или» модель делает несколько запросов. (Решение исполнителя-проектировщика.)
- Автоматическое исправление ответа после проверки.
- Запись в IACPaaS.
- Интеграция с VS Code (вне объёма по согласованию).

## Анти-цели

- Марка проходит условие «больше X» или «меньше X», хотя данные этого не гарантируют.
- Проверка выдаёт уверенный вердикт, не опираясь на данные из базы.
- Изменения ломают уже сохранённые диалоги или меняют формат ответов существующих инструментов так, что старые записи в истории перестают отображаться.

## Что решил автор

- Инструмент принимает структуру условий. Как он реализован внутри, не важно. Важно, что модель получает список марок или первую страницу, если марок много (порядка сотни и больше).
- Нужны: топ-N по содержанию элемента; «есть элемент» и «нет элемента»; комбинации («есть Cr и Br, нет Ni»); пороги «больше» и «меньше».
- **Сравнение по диапазонам, гарантированно.** «Больше X» — диапазон содержания целиком больше X, то есть нижняя граница > X. «Меньше X» — верхняя граница < X.
- Проверка ответов в два слоя: автоматическая сверка и отдельный агент-проверяющий. Агент запускается кнопкой на конкретном сообщении, а не флажком-режимом. Вердикт — в процентах или похожем виде.

## Часть 1. Инструмент поиска марок по составу

Имя: `find_materials` (решение исполнителя-проектировщика; в `docs/api-mapping.md` он закрывает `query_graph` из задания — «выполнить поддерживаемый запрос с ограниченными параметрами»).

### Вход

```json
{
  "conditions": [
    {"element": "Cr", "op": ">", "value": 20},
    {"element": "Mo", "op": "present"},
    {"element": "Ni", "op": "absent"}
  ],
  "material_class": "Сплавы на основе железа",
  "sort_by": "Cr",
  "order": "desc",
  "limit": 20,
  "offset": 0
}
```

- `conditions` — от 0 до 10 условий, все через «И». `op`: `>`, `>=`, `<`, `<=` (с `value` в процентах), `present`, `absent` (без `value`). У условий `<` и `<=` есть необязательный флаг `include_unlisted` (по умолчанию `false`, см. «Условия»); у остальных он даёт `INVALID_CONDITION`.
- `element` — символ элемента. Русское название («хром») принимается, если оно есть в базе элементов. Неизвестный символ — не ошибка: результат пустой, с явной пометкой (см. «Выход»).
- `material_class` — необязательно. Имя класса или подкласса без учёта регистра, включая все вложенные классы. Неизвестный класс — ошибка `UNKNOWN_CLASS` со списком классов.
- `sort_by` + `order` (`desc` по умолчанию) — необязательно. Сортировка по содержанию элемента; `sort_by` подразумевает условие `present` для этого элемента.
- `limit` от 1 до 50 (по умолчанию 20), `offset` от 0. Без условий и без сортировки инструмент возвращает марки по алфавиту (обзор), с той же постраничностью.

### Как значения превращаются в диапазоны

| Форма записи | Диапазон [низ, верх], % |
|---|---|
| Интервал a–b | [a, b] |
| Не более X | [0, X] |
| Не менее X | [X, 100] |
| Число X | [X, X] |
| Расчетное, Совокупность, нет значения | неизвестен |

### Условия

- `> X`: низ > X. `>= X`: низ ≥ X. `< X`: верх < X. `<= X`: верх ≤ X. Это решение автора: только гарантированное выполнение.
- Марки, в составе которых элемент не указан, условие `<` / `<=` по умолчанию не проходят: отсутствие в записи не означает 0 %. Если у условия `include_unlisted: true`, такие марки проходят и в `contents` помечаются формой «не указан в составе» (`low` и `high` — `null`). Модель включает флаг, когда вопрос подразумевает и марки без элемента («где никеля меньше 1 %»). Решение автора. Масштаб по индексу: для `Ni < 1` проходят 672 марки с указанным никелем и ещё 339 без никеля в составе.
- `present`: элемент перечислен в составе марки в любой форме, включая «не более». Чтобы потребовать гарантированного присутствия, модель передаёт `> 0`. (Решение исполнителя-проектировщика.)
- `absent`: элемент не перечислен в составе.
- Элемент с неизвестным диапазоном считается присутствующим, но не проходит ни одно числовое условие.
- Элемент, которого нет ни в одном составе (любой символ вне 32 элементов из раздела «Данные», например Br или W): `present` и числовые условия не выполняются ни у одной марки, а `absent` выполняется у всех. Символ попадает в `elements_not_in_compositions`. (Решение исполнителя-проектировщика.)

### Сортировка

По убыванию: сначала по нижней границе, при равенстве — по верхней. По возрастанию — наоборот. Тогда записи «не более X» (пределы примесей, низ = 0) оказываются внизу рейтинга. Марки с неизвестным диапазоном идут в конец. (Решение исполнителя-проектировщика, согласовано с автором как часть предложения.)

### Выход

```json
{
  "ok": true,
  "data": {
    "total": 37,
    "materials": [
      {"node_id": "381405980786784", "name": "12Х18Н10Т",
       "class": "Сплавы на основе железа", "base": "Fe",
       "contents": {"Cr": {"form": "Числовой интервал", "low": 17.0, "high": 19.0, "text": "17.0–19.0 %"}}}
    ],
    "has_more": true, "next_offset": 20,
    "rules": "«> X» — нижняя граница диапазона больше X; «< X» — верхняя граница меньше X",
    "elements_not_in_compositions": []
  },
  "meta": {"served_from": "local_index", "indexed_at": "…"}
}
```

- В `contents` — только элементы, которые упомянуты в условиях или в `sort_by`, в исходной форме записи и в виде диапазона.
- `elements_not_in_compositions` — элементы из запроса, которые не встречаются ни в одном составе (например, Br). Модель по нему говорит «в составах не встречается», а не «не найдено из-за ошибки».
- Ответ подчиняется общему лимиту размера (`MAX_RESULT_CHARS`, сейчас 22 000 символов): если страница не помещается, она укорачивается с `has_more` и `next_offset`, как у других инструментов.
- Ошибки — результатом с кодом, как у остальных инструментов: `UNKNOWN_CLASS`, `INVALID_CONDITION` (например, `>` без `value` или `present` с `value`), `LIMIT_EXCEEDED`, `INDEX_NOT_READY`.

### Источник данных

Локальный индекс, то есть снимок с датой `indexed_at`, как у `search_graph`. Нужные марки модель затем читает с платформы через `get_subgraph`. Таблицу состава (марка, класс, основа, элемент, низ, верх, форма, исходный текст) рекомендуется строить из таблиц `nodes` и `edges` индекса при импорте ресурса, в той же транзакции. Для уже существующего индекса таблица должна появиться без повторной синхронизации с платформой: например, строиться при первом обращении, если её нет. Выбор места и способа — за исполнителем. Ориентир по скорости: запрос по всем 1 334 маркам — доли секунды.

### Что поменять вокруг

- Описание инструмента (docstring) для модели: когда его использовать, правило «гарантированно», `present` против `> 0`, постраничность.
- Промпт (`prompts.py`): вопросы о марках по составу (больше/меньше X % элемента, топ по элементу, есть/нет элемента, в каком классе) решаются через `find_materials`, а записи потом читаются через `get_subgraph`.
- Журнал в интерфейсе: ярлык в `TOOL_ACTIVITY` (например, «Подбирает марки по составу») и короткая сводка аргументов («Cr > 20 · нет Ni · Сплавы на основе железа»).

### Проверка готовности (на реальном индексе)

Исполнитель считает ожидаемые ответы независимо (прямым обходом индекса в тесте или скрипте) и сравнивает:

- `Cr > 20` — ни у одной марки в выдаче нижняя граница хрома не ≤ 20; 12Х18Н10Т (17–19) не попадает.
- `sort_by=Cr, limit=3` — первые три совпадают с независимым подсчётом.
- `Cr present` и `Ni absent` — в выдаче нет марок с никелем в составе.
- `Fe >= 25` — выдача постраничная, сумма страниц равна `total`.
- `Br present` — `total: 0`, Br в `elements_not_in_compositions`.

## Часть 2. Автоматическая сверка чисел

- **Когда.** После каждого ответа модели, без дополнительных вызовов модели. Чистая функция в отдельном модуле, вызывается в конце хода (агент или веб-слой — на выбор исполнителя).
- **С чем сверять.** Числа из данных в результатах инструментов этого хода и прошлых ходов того же диалога (у модели есть право отвечать по найденному ранее). Источник — сохранённый `trace`, в нём полные результаты. (Решение исполнителя-проектировщика.)
  - Данными считаются поля вершин и записей: `label`, `value`, `comment`, `name`, `path`, `node_id`, `id`, содержимое `contents` у `find_materials`, а также `total`.
  - Служебные поля — `limit`, `offset`, `next_offset`, `children_not_loaded`, `duration_ms`, даты `indexed_at` и `fetched_at` — не учитываются. Иначе небольшие целые в ответе «подтверждались» бы случайно.
  - Числа, которые есть в вопросе пользователя или в аргументах вызовов (порог «20» в «Cr > 20», «3» в «топ-3»), не помечаются как ненайденные и не входят в счёт подтверждённых. Отдельной категорией они не показываются.
- **Что извлекать из ответа.** Отдельные числа: десятичная точка или запятая, пробел как разделитель тысяч («2 670»), диапазоны «17–19» как два числа, длинные `id` вершин (их тоже сверять).
- **Что не считать.** Маркеры нумерованных списков в начале строки, числа внутри слов с буквами (марки «12Х18Н10Т», «АК4-1», «Б83»), даты вида «21.10.2026». (Решение исполнителя-проектировщика.)
- **Как сравнивать.** По значению: «17», «17.0» и «17,0» — одно число.
- **Что видит пользователь.** Под ответом строка вроде «Числа сверены с данными: 12 из 12» или «Не найдены в данных: 9500, 10300 — проверьте». Такие числа желательно подсветить в тексте ответа. Формулировка нейтральная: числа, вычисленные моделью (пересчёт единиц, суммы), сюда тоже попадут, и это не обязательно ошибка. Если в ходе не было данных из базы, а числа в ответе есть, пишется «нет данных для сверки».
- **Хранение.** Результат сверки сохраняется вместе с ответом (новая колонка в `messages` с миграцией) и показывается при повторном открытии диалога. В поток уходит отдельным событием или в составе `answer_meta` — на выбор исполнителя, с обновлением `docs/http-api.md`.

## Часть 3. Агент-проверяющий (кнопка «Проверить»)

- **Интерфейс.** Кнопка «Проверить» в строке под каждым ответом ассистента, рядом с «Копировать». После нажатия — «Проверяю…», затем под сообщением блок вердикта. В нём итог «Подтверждено 11 из 12 утверждений (92 %)» и раскрываемый список утверждений со статусом («подтверждено», «нет в данных», «противоречит данным») и опорой: `node_id` и короткая выдержка. Повторная проверка заменяет прежний вердикт.
- **API.** `POST /api/sessions/{session_id}/messages/{message_id}/verify`. Ответ — JSON с вердиктом и расходом; поток не обязателен. Пока в диалоге формируется ответ, проверка возвращает 409, как второй вопрос. (Решение исполнителя-проектировщика.)
- **Проверяющий.** Отдельное обращение к модели без инструментов: он судит только по тому, что реально пришло из базы. Это решение автора. Провайдер тот же (RouterAI). Модель — из новой настройки `VERIFIER_MODEL`, по умолчанию `ROUTERAI_MODEL`.
- **Что получает проверяющий.** Вопрос пользователя, текст ответа, результаты инструментов этого хода и прошлых ходов диалога из сохранённого `trace`. Всё это укладывается в бюджет контекста, при переполнении — понятная ошибка.
- **Что делает проверяющий.**
  - Разбивает ответ на атомарные утверждения о данных: числа, принадлежность элемента марке, наличие свойства, «не найдено».
  - Каждое помечает как подтверждённое (с опорой), отсутствующее в данных или противоречащее им.
  - Реплики о диалоге и предложения помощи пропускает.
  - Вычисленные утверждения (пересчёт единиц, рейтинг) считает подтверждёнными, если они выводятся из данных арифметически.
- **Формат ответа проверяющего.** Структурированный (pydantic-модель). Способ получения — через вызов функции (`with_structured_output` с function calling: модель DeepSeek поддерживает tool calling) или JSON-режим, на выбор исполнителя. Нераспознанный ответ — понятная ошибка в интерфейсе, а не пустой вердикт.
- **Итог.** Процент = подтверждённые / все проверенные утверждения. Словесный вердикт: «подтверждён» при 100 %, «частично подтверждён» от 70 %, ниже — «не подтверждён». (Пороги — решение исполнителя-проектировщика.)
- **Расход.** Токены и стоимость проверки показываются в блоке вердикта и прибавляются к стоимости диалога. Вердикт с расходом сохраняется в новой колонке `messages` с миграцией.

## Часть 4. Исправление `fields_truncated`

`GraphService._bounded_node` ставит `fields_truncated: true` каждой вершине со ссылкой, потому что сравнивает ссылку после перевода в короткий путь (без «владелец / Мой Фонд») с исходной. Пример — у вершины «Плотность вещества» в базе элементов: ничего не обрезано, а признак стоит. Признак должен ставиться только при реальном усечении: обрезка по длине или ссылок больше трёх. Нужен тест.

## Объём по заходам

Решение автора: работа идёт в два захода, каждый выполняют субагенты по плану. Краткая версия решений для читателя без контекста — раздел «План доработок» в `README.md`.

**Заход 1** — части 1–4 этого документа и ещё три правки:

1. В описании `search_graph` (`mcp_server.py`) указать, что `limit` — до 20, и объяснить: поиск идёт по полной копии ресурсов, `has_more: false` значит «найдено всё».
2. Промпт (`prompts.py`):
   - не писать оговорку «записи могли не попасть в индекс»; если данных мало, писать «заполнено у N записей»;
   - примеры вопросов при отказе брать из тех, на которые в данных есть ответ (например, из `suggested_questions` в `config/data_notes.json`);
   - вопросы о максимуме, минимуме и количестве марок по составу решать через `find_materials`, остальные — дочитывать страницы до `has_more: false`.
3. Подсказка у пометки источника в журнале (`static/trace.js:195`) показывает «Платформа: [object Object]», потому что подставляется объект `{code, message}`. Должен показываться текст `message`.

**Заход 2** — отдельно, после завершения первого:

1. Повторный одинаковый вызов инструмента (то же имя и те же аргументы) в одном ходе не выполнять, а вернуть короткий результат «этот вызов уже был на шаге N, используйте его результат». Это правка `TurnPolicy` в `agent.py` с тестами.
2. Проверка устаревания индекса: выгрузка с `export-depth=0` возвращает корень ресурса с датой изменения. Сверять её с датой в индексе при старте (и, возможно, периодически) и пересинхронизировать только изменившиеся ресурсы. Детали — в начале захода 2.

## Ограничения

- Python 3.12, зависимости из `requirements-lock.txt`. Новые пакеты не добавлять без необходимости: pydantic, LangChain и httpx уже есть.

- Документация обновляется под новое поведение: `docs/guide.html` (инструментов станет 7; «6 инструментов» и «шесть» встречаются в строках около 159, 198, 248, 318, 342, 358, 900; число тестов), `docs/api-mapping.md` (новая строка и `query_graph`), `docs/http-api.md` (новый эндпоинт и поле или событие сверки), `README.md`.
